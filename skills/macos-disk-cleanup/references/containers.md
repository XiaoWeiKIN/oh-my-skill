# 容器和虚拟机

## Docker

1. 记录 Docker Desktop 是否运行、已有运行容器和磁盘基线。未运行时先检查本地磁盘文件；如需启动引擎进行已授权的 Docker 清理，说明启动会可能触发容器自动重启。结束后恢复本次改变的运行状态，避免影响后来新启动的工作。
2. 使用 `docker system df -v`、容器和镜像列表、volume inspect 分类。区分构建缓存、无标签镜像、未使用但可重新拉取的镜像、本地独有镜像、数据卷。不要将“未运行”当成“无数据价值”。
3. 枚举包括停止容器在内的挂载关系，并查询 `docker volume ls --filter dangling=true`。隐藏的 Kubernetes 引用可能未出现在普通 `docker ps -a` 中；无可见引用不是充分证据。卷内检查需要时使用临时只读挂载、禁网、用完删除的辅助容器，不启动卷中的服务。
4. 仅删除用户授权的具体卷；daemon 拒绝删除在用卷是最终约束。保留并解释，不强制、不删除宿主机或虚拟机内的原始卷文件。已授权清理“孤立旧 ClickHouse 卷”不等于可清所有 dangling 卷。
5. 不以 `docker system prune --volumes` 代替明确范围，不直接修改 overlay2、容器元数据或其他引擎内部存储。日志通过受支持的容器／应用机制处理。
6. 清理后核验保留的容器、镜像和卷。辅助容器应删除；本次新拉取且未被使用的辅助镜像可在授权范围内回收。

## Docker.raw 与回收差异

对实际磁盘镜像使用 `ls -lh` 和 `du -k` 区分逻辑容量与已分配空间。容器内释放不一定立即缩小宿主机分配量。

需要额外回收时，查阅当前官方 Docker Desktop 文档，核对本机版本与架构支持的回收方式。特权回收容器仅在官方当前支持、作用与授权一致时使用；不要照搬历史命令。不得手动截断 Docker.raw 或把删除整个镜像当成普通缓存清理。最终用宿主机 `df` 和镜像 `du` 验证。

## Podman 与 Minikube

先用其 CLI 查看 machine/profile、运行状态、卷和磁盘位置。机器或 profile 包含用户工作负载，不能当作下载缓存删除。

用户明确授权旧环境整体删除时，优先通过对应 CLI 删除指定 machine/profile，再检查残余缓存。Minikube 的主机缓存、profile 和 Docker driver 数据卷分别核实；不要顺带删其他 Kubernetes 环境或通用 kubeconfig。保留现有容器关联的数据卷时，该限制优先于泛化的环境清理。
