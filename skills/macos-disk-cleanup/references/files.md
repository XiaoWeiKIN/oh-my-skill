# 文件类清理判据

## 开发依赖和产物

`node_modules`、Go 编译缓存、包管理器下载缓存通常可重建，但需区分依赖目录与运行中的应用依赖，并保留锁文件。模块缓存、SDK、全局工具链可能涉及离线工作和重下载成本，作为独立候选展示。

`build`、`target`、`dist` 只是名字。定位最近的 Git 仓库，检查 `git ls-files` 中是否有目标下的已跟踪文件、`git check-ignore` 的规则，以及目录内容与构建配置。已忽略不等于可删，仍需确认不是数据库或交付成品。非 Git 项目依据构建配置和内容判断；证据不足时跳过。检查运行中的 jar、进程工作目录和文件句柄，保留仍在使用的产物。

不要删除 `.git`、未提交源码或用普通 rm 清理托管 worktree；Codex 托管 worktree 使用应用提供的归档能力，确认所需忽略文件已保留。

### Go 编译缓存与模块缓存

分别运行 `go env GOCACHE GOMODCACHE` 定位，不能把两者混为一项。用户保留模块缓存时，仍可独立评估编译缓存。

清理编译缓存前重新核对 GOCACHE 是否仍是已批准路径，确认没有正在使用该缓存的编译任务；优先执行 `go clean -cache`。不要附带 `-modcache`、`-fuzzcache` 或删除整个 Go 工作目录。说明下次编译需要重建缓存，结束后测量剩余占用及磁盘可用空间净变化。

### IDE 和构建工具缓存

- JetBrains 的 `index`、`caches` 可作为重建型缓存候选，逐个确认产品、版本与项目使用情况，退出对应 IDE 后处理。不能删除整个版本目录；保留 LocalHistory、本地历史、恢复数据、配置和未知用途文件。提醒下次打开项目需要重新索引。
- VS Code 的 `CachedExtensionVSIXs` 是扩展安装包缓存，与 `.vscode/extensions` 中已安装扩展分开处理；确认没有安装／更新任务后再清理。
- `Library/Caches/node-gyp` 中的版本化头文件属于可重新下载的构建缓存；确认无原生模块构建，提示后续构建可能需要联网，保留 Node 安装和项目依赖。

## 应用缓存、更新包和重复备份

区分 Cache／Code Cache／下载的安装包与配置、登录态、IndexedDB、聊天数据库和媒体。不递归删除整个 Application Support 或应用容器。媒体是用户数据，不能承诺可重新下载。

旧更新包需对比已安装版本、更新时间和打开状态；VS Code 旧扩展结合 `.obsolete` 和实际安装版本确认，缓存 VSIX 与正在使用的扩展分别处理。

待安装更新不是旧包。对比实际安装版本与包内 app 的 Info.plist：较新的下载包默认保留；用户明确点名要求清理后，已有授权即可执行，无需重复确认。检查更新器没有正在安装或读取，删除仅限选中的下载包及其解包副本，不扩展到整个更新器目录、已安装应用或应用数据。明确说明这是丢弃待安装更新，日后升级可能需要重新下载。

### Claude Code 原生安装旧版本

定位 `~/.local/bin/claude` 的实际链接目标和 `~/.local/share/claude/versions`（以本机安装方式为准）。检查其他入口、正在运行的版本、文件引用和更新任务；保留当前链接指向版本及任何仍被引用的版本。仅将确认未使用的旧二进制列为候选，不按固定版本号或“除最新外全删”推导范围。执行前复核当前入口没有变化，清理后确认入口仍可解析到保留文件。不要删除 Claude 配置、会话或其他安装方式的文件。

重复备份按相对路径、文件内容哈希和缺失项验证，明确保留哪份。仅相同名称或大小不算重复；硬链接或 APFS 克隆即使内容相同，也未必可回收所见大小。

Chromium 等目录中的 `.code_sign_clone` 可能共享 APFS 块。不要把其 `du` 总和当成保证可释放量；结合版本和使用状态判断，未授权不删除。

## 临时目录

`/private/tmp` 不等于可以全删。它可能含活动 socket、浏览器目录、Git 仓库、唯一脚本、补丁、视频成片、数据库和其他用户的文件。

按精确路径和明确来源识别缓存、临时依赖及构建预览，排除保留项和活动进程引用。年龄只作线索，不单独作为删除依据。不跟随符号链接，不清扫其他用户／系统对象。仅凭 `.js`、`.json` 等扩展名不能判断为产物。

## 日志与“删完又涨”

使用定向 `lsof -nP`、进程工作目录、程序身份定位写入者；没有 lsof 命中并不证明以后不会使用。日志目录总量、各文件增长和进程归属分开说明。

- 不再被打开的旧日志可在授权范围内删除。
- 仍在写的普通日志，在已授权清理日志的范围内可原地截断，保留 inode；实现时用不跟随链接的打开方式，核验普通文件再 ftruncate。不要误删 `.pid` 或把数据库 WAL 当普通日志。
- 用户要求“关闭”后核验具体 PID 对应服务，再正常终止并确认退出；不按宽泛关键词杀进程。若由 supervisor 重启，识别对应启动项后再在授权范围内处理。

### RocketMQ 与 Java 调试日志

`~/logs/rocketmqlogs` 和项目 `.runlogs` 是定位线索，不是通配删除范围。先列出大日志的大小、修改时间及写入者；RocketMQ 客户端日志可能由业务 Java 服务产生，不代表本机运行了 RocketMQ broker。

服务正常停止且日志不再被打开后，只删除已授权的日志文件，保留 `.pid`、配置、构建产物和源码。不要直接删除 `.runlogs` 父目录；日志扩展名也不能替代内容用途判断。若日志再次增长，定位当前写入者；需要用户授权才能停止新的服务，不复用旧 PID。
