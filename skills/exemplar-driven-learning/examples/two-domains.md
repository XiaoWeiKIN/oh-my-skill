# Two Worked Learning Scopes

本文件展示如何规划研究，**不是**对这些项目当前版本的实证结论。真正研究时应重新核对官方资料、源码版本和用户约束。

## 场景一：通过顶级项目学习 Go 大型系统工程

用户请求：“学习 Go，我想重点看 Kubernetes、VictoriaMetrics、OpenTelemetry、Grafana。”

### 先区分目标

Go 的语法、内存模型、并发语义与标准库，应以语言规范和官方资料为基础；大型项目承担“工程设计实战”的任务。

研究问题：
1. 模块、扩展点与配置生命周期如何组织？
2. 控制循环与状态一致性如何设计？
3. 高吞吐服务如何做并发控制、内存利用和降级？
4. 代码组织、测试和性能回归如何支持长期演进？

### 选择与分工（研究假设）

| 案例 | 主要研究问题 | 关键追踪路径 | 需警惕的局限 |
| --- | --- | --- | --- |
| Kubernetes | 声明式状态、Controller/Reconciliation | API 对象 → 期望状态 → 调谐 → 状态写回 | 平台级复杂度不能原样引入小项目 |
| VictoriaMetrics | 时序存储、性能与并发权衡 | 写入/索引/查询中的一个请求路径 | 不同部署模式与负载应区分 |
| OpenTelemetry Collector | 组件 Factory、Pipeline、扩展 | 配置 → 组件创建 → pipeline 数据流 | Collector 与全部 OTel SDK 不能混称 |
| Grafana | 大型产品架构、插件与界面协作 | 插件生命周期/后端接口的公开路径 | 项目跨语言，不能全部当作 Go 范本 |

每个问题只深挖最相关的两个案例。不要把所有仓库都按目录从头读完。

### 首个可操作实践

实现一个可注册的微型采集 Pipeline：
- 研究问题：组件如何依据配置装配，如何传播生命周期与错误？
- 测试：一个有效配置成功运行；一个非法配置在启动前明确失败。
- 对照：同样问题若用静态构造而非插件式注册，复杂度和扩展成本如何变化？
- 证据：在固定版本上运行真实单元测试后再记录执行结果；目前仅为研究计划。

## 场景二：通过标杆理解可观测性产品

用户请求：“以 OpenTelemetry、Datadog、Dynatrace 为主学习可观测性产品。”

### 先分层

| 层次 | 代表对象 | 问题 |
| --- | --- | --- |
| 数据标准与采集 | OpenTelemetry | 数据、语义约定、上下文传播如何互操作？ |
| 用户工作流与分析产品 | Datadog | 如何从告警/服务进入 trace、过滤、聚合与定位？ |
| 自动发现与诊断产品 | Dynatrace | 如何关联服务、依赖、问题与诊断结果？ |
| 存储与查询（如研究目标需要） | VictoriaMetrics、ClickHouse 等 | 数据如何写入、查询、保留与控制成本？ |

**重要：** OpenTelemetry 不是与两个商业产品完全同层的替代品。横向对照“产品能力”时，应选择同层对象；研究端到端可观测体系时，可比较它们的分工与接口。

### 从一个用户问题贯穿研究

学习问题：“生产延迟突然升高，平台如何帮助用户定位责任服务和关键请求？”

按统一路径调查：
1. 数据从哪里来，哪些语义属性保证可关联？
2. 用户从何种入口发现问题，如何收窄查询范围？
3. 服务拓扑、Trace、Metrics、Logs 如何关联？
4. 查询的时间范围、采样和保留策略怎样影响结论？
5. 哪些推断可核实，哪些属于产品提供的解释？

### 最小迁移实践

在自有 APM 原型设计“服务 → Trace 查询 → 单条 Trace 详情”的三段路径。
- 提前写下可观察验收：筛选条件是否保留、上下文能否传播、数据缺失时是否明确提示。
- 同时准备一个不存在完整 Trace 的反例，检验 UI 是否错误宣称因果诊断。
- 仅在实际操作对标产品与运行原型后，才报告功能等价或差距。

## 防止错误学习的反例

差的结论：“Kubernetes 使用某种复杂抽象，因此任何 Go 服务都必须采用它。”

可迁移结论：“当系统确有声明式期望状态、持续漂移和异步收敛问题时，考虑调谐循环；如果只是同步请求处理，应先评估更简单的流程。需要用失败恢复场景验证。”
