# Exemplar-Driven Learning

用少数有代表性的优秀案例覆盖一个领域的重要设计空间，并把研究结果变成可迁移的判断能力。

**核心循环：问题 → 代表案例 → 约束与机制 → 横向对照 → 实验验证 → 可复用原则。**

## 适用边界

- 用于制定学习路线、开展架构/产品研究、从项目中学习工程实践、形成跨案例设计原则。
- 用户指定了案例时，优先研究指定案例；只有明显缺少关键设计维度时才建议补充。
- 不要把语言基础、标准、官方规范、论文等一手知识全部替换成案例阅读。案例用于解释“知识如何被用于真实决策”。
- 不把人气、GitHub stars 或市场份额直接视为最佳实践证据；不宣称少数案例可覆盖所有场景。
- 纯写作、美化现有文档等任务交给 `doc-writing`；将研究结果持续写入 Obsidian 时协同 `llm-wiki-maintainer`，未经授权不写入知识库。

## 工作流

### 1. 定义要学会的决策

从用户请求和已有上下文提取：目标领域、能力层级、当前问题、适用约束、预期产出。已明确的信息不再反复追问。

将“学习 Go / 可观测性”转为 3–7 个可以检验的关键问题，例如“服务如何实现可扩展的组件装配？”或“高查询并发下如何隔离长查询？”。区分基础知识、工程架构和产品设计；不要把不同层次混为同一个选型问题。

先输出一句学习目标：**完成研究后，学习者应能够独立作出什么判断或完成什么设计？**

### 2. 选择覆盖设计空间的案例

先列出核心设计轴，再挑选能够在不同轴上提供证据的案例。一般优先 2–4 个深入研究对象，数量由覆盖缺口决定，而非硬性凑数。

评估每个候选的：
- 代表性：真实、长期或有重要影响的实践；注明适用的规模与场景。
- 差异性：是否展示了另一条路线或不同的设计权衡。
- 可研究性：是否有一手文档、源码、设计提案、公开技术分享或可运行实例。
- 可迁移性：用户的目标中有哪些问题确实与其相似。
- 盲区：商业闭源、缺少决策记录、历史遗留、无法复现等限制。

允许增补一个反例或对照案例来纠正幸存者偏差。**不能用多个同质化成功案例冒充全面覆盖。**

选择时读 [references/research-protocol.md](references/research-protocol.md) 中的设计空间表与证据分级规则。

### 3. 按相同问题剖析案例

对每个案例回答六个问题：

1. **问题**：它要解决什么，目标用户/工作负载是什么？
2. **约束**：规模、时延、成本、组织、兼容性、演进历史有哪些硬条件？
3. **不变量**：必须保证什么性质或行为？
4. **机制**：关键组件、数据流、控制流和边界如何协作？
5. **取舍**：牺牲了什么、替代方案是什么、在哪些前提下设计会失效？
6. **证据**：哪份设计文档、源码、测试、产品行为或实验支持这一判断？

解释“为何如此设计”，不默认逐文件阅读源码。需要深入时沿请求路径、状态流转或数据流选取少数关键模块追踪；给出可核对的文件路径、版本或文档链接。

### 4. 横向对照并提炼规则

**先按问题对齐，再比较答案。** 以“问题 → 案例 A/B/C 的处理方式 → 制约因素 → 适用边界”组织矩阵。

分清：
- 共性：跨项目都成立的约束/机制，仍注明条件。
- 分歧：因工作负载、团队、产品定位或技术路线不同而产生的选择。
- 未决：缺少证据、只是一种推测，或者证据与当前版本不一致。

提炼为条件化原则：**当 [条件]，为了 [目标]，优先 [机制]，代价是 [权衡]；当 [反条件]，考虑 [替代方案]。**

禁止把“某头部项目这样做”直接推导为“你也应该这样做”。

### 5. 用小型实践完成迁移

针对用户的真实项目选择最小可验证实践：设计一段接口、实现一个微型组件、复现一个查询/调度行为、做一次交互工作流对照，或写一份明确假设与验收条件的设计草案。

明确区分：
- **已执行**：提供实际命令、输入、输出、版本和正反向结果。
- **建议执行**：列出实验步骤与预期观察，不伪称已经验证。
- **不可验证**：指出访问限制与剩余未知。

实践至少检验一个成立条件和一个失效边界。没有工具或权限时只输出可复现的实验方案。

### 6. 输出问题驱动的知识结构

默认按照以下顺序交付：

1. 研究目标和问题清单。
2. 案例选择表：每个案例覆盖什么、为何入选、还有什么空白。
3. 关键机制对照：共同问题、不同方案、依据和约束。
4. 设计原则：有条件、有代价、有反例。
5. 迁移实践：最小任务、验收标准和未验证项。
6. 后续阅读：只列对尚未解决的问题有直接价值的一手资料。

简短请求可输出案例清单、选择理由与第一个研究问题；深入请求提供完整论证。**避免把输出组织成彼此孤立的“项目百科”。**

学习路线和交付模板见 [references/research-protocol.md](references/research-protocol.md)；Go 与可观测性场景见 [examples/two-domains.md](examples/two-domains.md)。

## 证据与质量门禁

- 优先官方文档、版本化设计提案、源码/测试、公开技术说明；社区总结只能补充，不能代替关键证据。
- 对随版本演变的系统记录仓库/文档版本和查询日期；无法访问实时来源时说明未核验。
- 区分事实、解释、推测；闭源系统的内部机制不得从 UI 表现臆测。
- 具体指标、架构选择、比较结论都要有相应来源或明确标为待验证。
- 当案例属于不同层次（标准、产品、存储引擎），分别研究其功能，再解释相互关系；禁止伪造同维度对比。
- 结束前检查：设计空间是否有重要缺口？是否理解关键机制的“为什么”？是否明确代价与反条件？是否能在用户场景中实践？

完成研究后，学习者应能回答：**若目标和约束变化，我将如何重新选择设计，而不是照抄标杆？**
