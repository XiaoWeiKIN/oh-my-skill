# Doc Writing

写文档不是填模板，而是用语言说服人、传递判断、推动决策。

在动笔之前，先用四个维度锁定上下文，否则写出的东西只是信息的堆砌，而不是文档。

---

## 第一步：建立写作上下文（开始写之前必做）

向用户确认（或从对话中推断）以下四个维度：

**1. 目的与受众**
- 这篇文档要让读者做什么决定、采取什么行动？
- 读者是谁？他们已经知道什么、最关心什么？
- 在哪个场景下被阅读（会议前预读、异步评审、存档备查）？

**2. 风格定调**
文档风格决定语气和结构选择，常见方向：
- **决策驱动**：结论前置，每节都服务于一个明确主张
- **叙事推进**：背景→问题→洞察→方案，像讲故事一样展开
- **对比分析**：多方案并列，优劣势直接可见
- **操作手册**：步骤清晰，每步有可验证的产出

**3. 约束条件**
- 篇幅要求（一页纸 / 详细方案 / 执行手册）？
- 是否需要同步到飞书、是否需要符合项目 front matter 规范？
- 时间背景、技术栈、术语规范等上下文约束？

**4. 差异化记忆点**
读者读完这篇文档，应该记住什么？一句话能说清楚吗？如果说不清楚，文档的核心主张还没想清楚，先别动笔。

---

## 第二步：五个写作维度

确定上下文后，在这五个维度上做出主动选择——不要让它们默认滑向平庸。

### 1. 结构层次

结构是读者理解文档的地图，要主动设计，而不是「先写再说」。

- **金字塔原则**：结论放最前，理由支撑结论，细节支撑理由。读者可以在任何层级停下来
- **每个章节有且只有一个核心主张**，章节标题本身就应该能传达这个主张（「方案选型」比「三种方案对比」弱，「选 B 方案，因为迁移成本最低」更强）
- **避免「背景 + 现状 + 问题 + 解决方案 + 总结」这种通用骨架**——这是信息的顺序，不是论证的顺序

### 2. 语言风格

- 每句话只承载一个意思，句子长度控制在 30 字以内
- 用主动语态，避免「需要被关注」「应当进行」这类无主语的被动句
- 用具体数字替代模糊程度词：「减少 60% 的接口调用」优于「显著降低」
- **不写废话**：「本文档旨在……」「综上所述……」「在当前背景下……」这类开头/结尾句一律删掉
- 关键概念第一次出现时用**加粗**，之后无需重复加粗

### 3. 信息密度

信息密度不是越高越好，而是要匹配读者和场景：

- **决策层读者**：高密度，结论 + 关键依据，背景可以极简
- **执行层读者**：中密度，步骤完整，有足够上下文但不需要历史背景
- **外部读者**：低密度，概念需要解释，节奏放慢

常见的密度错误：技术细节淹没了核心判断；或者为了「显得全面」把所有信息都塞进来。

### 4. Markdown 排版

排版是阅读体验，要主动服务于内容层级，而不是为了排版而排版：

- **标题层级**：H1 是文档标题，H2 是主要章节，H3 是子节——不要为了加层级而加层级
- **列表**：用于并列项（三个以上），不要把逻辑推理拆成列表（「因为 A / 所以 B / 因此 C」是段落，不是列表）
- **表格**：用于对比多个维度，不要把两列的简单对应关系做成表格
- **加粗**：用于关键术语和核心结论，每段最多 1-2 处，不要全文加粗
- **代码块**：命令、配置、代码片段必须用代码块，不要混在正文里

### 5. 核心主张

这是最重要的维度。每篇文档都应该有一个中心论点，整个文档都在为它服务。

问自己：**如果只能保留一句话，这篇文档想说的是什么？**

如果这句话是「介绍了 XXX 的现状和未来规划」，那还没有核心主张。
如果是「我们应该在 Q2 优先投入 XXX 而不是 YYY，因为 ZZZ」，这才是主张。

有主张的文档才能推动决策；没有主张的文档只是记录。

## 第三步：写作原则

### 必须做

- ✅ **结论前置**：第一段告诉读者你要说什么，剩下的是为什么
- ✅ **每节标题传达主张**，不只是描述主题
- ✅ **写完后自检**：删掉第一段，文档是否依然完整？如果是，第一段是废话
- ✅ 优先遵循项目内现有规范文档（如 `AGENTS.md`、`README`、`docs/` 约定）；若没有，再遵循当前 Codex 会话中的写作与格式要求

### 不能做

- ❌ **不写「AI 味」的套话**：「在当今快速发展的……」「本方案旨在通过……实现……的目标」「综合以上分析……」
- ❌ **默认禁用「不是……而是……」式对照句**，包括「真正的……不是……而是……」「并非……而是……」「不只是……更是……」。这类句式常用虚构对立制造强调，连续出现时尤其像模板生成。直接陈述判断，例如把「关键不是写更多文档，而是建立更新机制」改成「关键在于建立文档更新机制」。只有在纠正读者已经明确提出的二选一误解时，才保留这种句式。
- ❌ **不写没有主语的虚化结论**：「需要进一步探索」「存在一定挑战」「值得关注」——谁需要？什么挑战？谁来关注？
- ❌ **不堆砌信息来显示全面**：选择比覆盖更重要，精准的三个要点胜过面面俱到的十个要点
- ❌ **不要凭空发明引用规范**：若项目已有文档链接规范，按现有规范；若没有，就使用可移植的标准 Markdown 链接

## 工作流参考

### 典型场景：从零写一篇方案

1. 用四维框架和用户对齐（1-2 轮问答，不要问太多）
2. 先写文档骨架（章节标题 + 每节一句核心主张），让用户确认方向
3. 填充内容，保持每节的主张明确
4. 自检：删冗余、加数字、改被动为主动；搜索「不是」「而是」「并非」「不只是」「更是」，改掉为了强调而虚构对立的句子
5. 如需同步到飞书文档，使用 `lark-doc` skill；如需在飞书里补图，使用 `lark-whiteboard` skill

### 典型场景：优化已有文档

1. 先读一遍，找出：主张在哪里？结构是否服务主张？有哪些废话？
2. 告诉用户你的诊断，再改
3. 改动要敢于删，不只是换词

### 配合其他 skill

| 需求               | 工具                    |
| ------------------ | ----------------------- |
| 同步到飞书         | `lark-doc`              |
| 查找参考资料       | `openai-docs` 或本地仓库检索 |
| 画架构图 / 流程图  | `lark-whiteboard` 或 Mermaid |


Remember: Codex should produce production-grade writing with a clear point of view. Keep the prose distinctive, concrete, and decision-oriented rather than generic.
